# TASK-010: 命名品質検査

| | |
| --- | --- |
| Phase | 2（検査） |
| 状態 | 未着手 |
| 依存 | TASK-007, TASK-008, TASK-009 |
| 規模 | 中 |

## 目的

`Path` と `EventName` が意味を持つ命名になっているかを検査する。

## 背景

将来の export（History/plan-viewHtmlExportFoundation.prompt.md、草案）は「**既存の命名が意味を持っていること**」に賭けている。

`OnIncrement` / `Count` / `TotalPrice` と命名されていればエージェントは読めるが、`OnClick01` / `Btn_Sub` / `Value2` では何も読めない。そして**現状のシステムは悪い命名を検出しない**。バインドは同じように通るため。

人の手を「注釈を書く作業」ではなく「規約違反を直す作業」に置き換える。前者は際限がなく腐るが、後者は有限で CI に載る。

**本タスクの出力が、export 計画に着手すべきかの判断材料そのものになる。** 違反が多ければ、作るべきは exporter ではなく命名規約である。

## 検査項目

| 検査 | 使用する API |
| --- | --- |
| **語幹が汎用語である名前**（後述） | TASK-004, `IViewEvent.Name` |
| 単一文字・2 文字以下の path / イベント名 | 同上 |
| 操作可能な `SemanticRole` を持つ要素にラベルが無い | TASK-008, TASK-009 |

ブロックリストは設定可能にする。プロジェクトごとに許容したい命名があるため。

### 「数字終端」を無意味名と判定してはならない

実プロジェクトでの実測により、**当初想定していた `Value\d+` / `Button\d+` のような単純な数字終端パターンは誤検出を大量に生む**ことが判明した。

実際の命名には**意味のある語幹＋連番**が多数存在する。

| パターン | 判定 |
| --- | --- |
| `<意味のある語幹><数字>`（所持品の連番、判定値の連番、選択状態の連番など） | **正当。検出してはならない** |
| `<汎用語><数字>`（`Button1`、`Value2`、`Item3`、`Obj1` など） | 無意味。検出する |

実測では、数字終端の path が全体の約 15% を占めるが、**そのほぼすべてが正当な連番**だった。イベント名側で真に問題があったのは全体の約 4% にとどまる。

**判定基準は「数字が付いているか」ではなく「数字を除いた語幹が意味を持つか」。** 汎用語のブロックリスト（`Button` / `Value` / `Item` / `Text` / `Obj` / `Panel` / `Image` など）と突き合わせ、**語幹が完全一致する場合のみ**検出する。

### 命名品質は既に高い（実測）

実プロジェクトの実測値。

| 対象 | ユニーク数 | 文字数（最短 / 中央値 / 最長） | 備考 |
| --- | --- | --- | --- |
| バインドパス | 438 | 3 / 10 / 25 | 意味のある名前が大半 |
| イベント名 | 113 | 4 / 9 / 23 | 87% が `On` 接頭辞 |

**export 計画が賭けている「既存の命名が意味を持つ」という前提は、実測上すでに成立している。** 本検査の役割は「賭けが成立しているかの判定」ではなく、**成立している状態を維持すること**に移る。

したがって**既定を警告に留める判断は妥当**（後述の備考を参照）。違反率が低いため、早期に失敗へ切り替えることも検討できる。

## 出力

違反件数だけでなく、**命名品質のサマリを出す**。

- 検査対象の Binder / Event 総数
- 違反件数と内訳
- 違反率

export 着手の判断に使うため、**推移を追える形で記録できる**ようにする。

## 対象ファイル

新規。`Unity/Assets/UVMBinding/Editor/Lint/` 配下。TASK-007 の走査基盤を再利用する。

## 完了条件

- 語幹が汎用語の名前（`Button1` 等）を検出できること
- **意味のある語幹＋連番（`HasItem0` 相当）を検出しないこと**
- ラベルの無いボタンを検出できること
- ブロックリストが設定で変更できること
- **既存プロジェクト全体に対して実行し、違反率を本ファイルに記録すること**
- メニューから手動実行でき、サマリが表示されること

## 備考

**既定を「失敗」にしない。** 既存プロジェクトに初めて流すと違反が多数出る可能性が高く、いきなりテストを赤くすると運用できない。まず警告として可視化し、違反率を下げてから失敗に切り替える。

CI は構築しない方針のため（2026-08-28 決定）、当面は手動実行と EditMode テストのみとする。

TASK-007 と同じくベースライン記録の仕組みが必要になる可能性がある。
